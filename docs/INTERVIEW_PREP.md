# Interview Prep

Guidance, not scripts — each answer points to the actual mechanism in this codebase. Open the referenced file if you need to refresh the details; don't memorize prose.

## Technical (20)

1. **Walk me through what happens when a member's contribution completes a cycle.** `contribution.service.ts` — the transaction is recorded, trust score adjusted, `cycle.totalCollected` incremented; if that meets the target (`contributionAmount × activeMemberCount`), a payout transaction fires, the recipient's membership flips `hasReceivedPayout`, and either the next cycle opens or the circle completes.
2. **How do you prevent a member from contributing twice to the same cycle?** A partial unique index on `Transaction` — `{cycleId, userId, type:'contribution'}` — enforced at the database level, not just checked in application code. A race between two requests still can't double-insert.
3. **Why is the ledger append-only, and how is that enforced?** Financial records shouldn't be editable after the fact — that's what makes a ledger trustworthy. `transaction.model.ts` registers `pre` hooks on `updateOne`/`findOneAndUpdate`/`deleteOne`/`findOneAndDelete` that throw, so it's enforced at the schema level, not by convention.
4. **How does the trust score work, and why that specific formula?** +1 for on-time, −5 for late, clamped 0–100. Deliberately asymmetric: one late payment costs more than one on-time payment earns back, so a high score has to be earned through consistency, not a single good month offsetting a bad one.
5. **What's a race condition you specifically guarded against here?** Two admins marking the same contribution simultaneously — closed by the DB-level unique index in #2, not a check-then-act application guard (which would still have a race window).
6. **How do you keep the frontend and backend validation in sync?** Both use Zod, with parallel schema files (`server/src/schemas/*` and `client/src/lib/validation/*`) expressing the same rules — not shared code, but the same validation library and intent on both sides of the boundary.
7. **Explain your API response envelope and why you standardized it.** Every response is `{status, data}` or `{status, error:{message}}` — the frontend never branches on response shape, and `getApiErrorMessage()` can unwrap any error uniformly.
8. **Describe a real bug you found while building this, not a hypothetical.** The login form's native HTML5 `type="email"` validation was silently intercepting submission before Zod ever ran — no error rendered, nothing sent. Caught with a real Playwright run, fixed with `noValidate` on the form.
9. **How do you handle a duplicate key error vs. a real database failure?** `isDuplicateKeyError()` checks `err.code === 11000` and converts it into a specific `ApiError.conflict()` with a human message; everything else falls through to a generic 500 so internals aren't leaked.
10. **Why Zod over something like Joi or express-validator?** One library, two runtimes (client + server), same mental model — schema-first, TypeScript-inferred types via `z.infer<>` instead of hand-written interfaces that can drift from validation.
11. **How would you add idempotency to the payment-verify endpoint?** It's already partially idempotent — a duplicate contribution insert fails on the unique index and surfaces as a 409, not a double-charge. A stricter version would key on the Razorpay `payment_id` itself before touching the ledger.
12. **What would break first under real load, and why?** Notification polling — every authenticated client hits `/notifications` every 30s regardless of activity. Fine at this scale; the honest next step is a websocket or at minimum a longer/backoff interval before Redis or anything heavier.
13. **How do you avoid leaking stack traces in production?** `errorHandler.ts` only includes `err.stack` when `NODE_ENV === 'development'`; the client always gets a clean message.
14. **What's the difference between authentication and authorization in this app, concretely?** `requireAuth` verifies *who* (valid JWT); `requireCircleAdmin`/`requireCircleMember` verify *what they're allowed to touch* — checked per-request against the actual resource, not inferred from a role alone.
15. **How do rate limits differ across your routes, and why?** 300/15min blanket on `/api`, 20/15min on `/auth` and payment routes specifically — credential and money-adjacent endpoints are the highest-value brute-force/abuse targets, so they get a tighter ceiling than a read-heavy endpoint like `GET /circles`.
16. **How did you verify code you couldn't run against a real database?** Unit tests with mocked Mongoose models (`vi.mock` on each model's module) isolate the actual business logic — cycle rollover, payout math — from the DB layer, which is the one thing that's still genuinely unverified.
17. **What's a design decision you'd defend even though it adds complexity?** The DB-level unique index for duplicate-contribution prevention (#2/#5) — an application-level check-then-insert would read simpler but has a real race window a unique index closes for free.
18. **What's a design decision you deliberately kept simple, and why?** No Redis, no websockets — notifications poll, there's no cache layer. Nothing at this scale needs them yet; adding them now would be solving a problem the app doesn't have.
19. **How do you structure error handling across async Express routes?** `asyncHandler()` wraps every controller, forwarding rejected promises to `next()` so a single `errorHandler` middleware handles all of them — no repeated try/catch per route.
20. **If you had one more week, what would you build?** Real database verification first (see README), then E2E tests, then email reminders — in that order, because the first two are trust-building for everything already written, not new surface area.

## Architecture (10)

1. **Why REST instead of GraphQL here?** The resource shape is stable and shallow (circles → cycles → transactions) — REST's simplicity wins over GraphQL's flexibility, which mostly pays off with deeply nested, client-varying queries this app doesn't have.
2. **Why service layer + controller separation instead of logic in controllers?** Controllers are a thin HTTP translation layer; services (`contribution.service.ts` etc.) hold the actual business rules and are what the unit tests import directly — no HTTP mocking needed to test business logic.
3. **How is authorization layered?** Two levels: route middleware (`requireCircleAdmin`/`requireCircleMember`) for the common case, and in-service checks (`dispute.service.ts`'s admin-or-platform-admin check) where the rule is more conditional than a single middleware can express cleanly.
4. **Why JWT over server-side sessions?** A decoupled SPA + REST API doesn't need server-side session state; JWT keeps the API stateless and horizontally scalable without a session store.
5. **Why an access token *and* a refresh token, instead of one long-lived token?** Short-lived access token limits the damage window if it's ever exposed; the refresh token is the only long-lived credential, and it's `httpOnly` so JavaScript — including an XSS payload — can never read it.
6. **How would this scale past a few thousand users?** The database queries are already indexed for the access patterns that matter (membership lookups, ledger reads); the first real bottleneck would be notification polling (#12 above), not the core data model.
7. **Why monorepo with npm workspaces instead of separate repos?** One `npm install`, one PR touching both sides of an API change, shared root tooling — the coordination cost of two repos isn't worth it at this size.
8. **What's your deployment target and why that split?** Frontend on Vercel (static + edge-friendly), backend on Render/Railway (long-running Node process), DB on MongoDB Atlas — standard separation of a stateless frontend, a stateful-ish API process, and a managed database.
9. **How do you keep the API contract from drifting between client and server?** Not fully automated here — the honest answer is parallel Zod schemas and manual discipline (see #6 in Technical), and a documented `docs/API.md` kept in sync by hand. A stricter setup would generate client types from the backend schemas.
10. **What would you change about this architecture if you started over?** Probably nothing structural — the layering (models → services → controllers → routes) held up cleanly as features were added across Phases 4 through 9 without needing a refactor.

## MongoDB (10)

1. **Why MongoDB over a relational database for this domain?** Circles/cycles/transactions are naturally document-shaped and don't need cross-table joins for the common read paths (a circle's member list, a circle's ledger) — though the *relationships* (memberships, ownership) still needed real referential discipline, which is why indexes matter as much as they do here.
2. **How do you enforce a relationship MongoDB doesn't enforce natively?** Application-level checks (does this `userId` have an active `Membership` in this `circleId`) backed by compound unique indexes where uniqueness actually matters — MongoDB won't stop you from creating orphaned references, so the service layer has to.
3. **Explain the partial unique index on `Transaction`.** `{cycleId, userId, type:'contribution'}`, `partialFilterExpression: {type: 'contribution'}` — unique only among contribution-type documents, so payout transactions (which share `cycleId`+`userId` shape) aren't caught by the same constraint.
4. **What indexes does this app rely on, and why each one?** `User.email` (unique, login lookups), `Circle.inviteCode` (unique, join lookups), `Membership {circleId, userId}` (unique, prevents double-join), `Cycle {circleId, cycleNumber}` (unique, prevents duplicate rotation slots), `Transaction {cycleId, userId, type}` (partial unique, #3).
5. **How do you handle schema validation — Mongoose or MongoDB's own JSON schema validator?** Mongoose schemas, backed by Zod at the API boundary before data ever reaches Mongoose — two layers, but for different purposes (Zod = request shape, Mongoose = persistence-layer types/defaults).
6. **What's `InferSchemaType` doing for you?** Derives the TypeScript type for a Mongoose document directly from the schema definition, so the model and its type can't silently drift apart the way a hand-written interface could.
7. **How would you paginate the ledger endpoint if a circle ran for years?** It's currently capped at 200 with a `createdAt` sort — the real fix is cursor-based pagination on `createdAt`/`_id` rather than offset pagination, which degrades on large collections.
8. **What happens on a duplicate key violation, end to end?** Mongoose throws with `err.code === 11000` → `isDuplicateKeyError()` catches it in the service → converted to `ApiError.conflict()` → the client gets a clean 409 with a specific message, never a raw Mongo error.
9. **Why block updates/deletes on `Transaction` at the schema level instead of just not writing update code?** Discipline enforced by the framework survives future contributors (or future you) who don't know the convention — a `pre` hook that throws is a guarantee, "don't write update code" is a hope.
10. **How do you connect to MongoDB, and what would you change for production?** `mongoose.connect(env.MONGODB_URI)` with `strictQuery` enabled; for production I'd add connection pooling tuning and `mongoose.set('sanitizeFilter', true)` as one more injection-defense layer alongside `express-mongo-sanitize`.

## React (10)

1. **Why TanStack Query instead of just `useEffect` + `fetch`?** Caching, request de-duplication, loading/error states, and background refetching come for free — hand-rolled `useEffect` data fetching reimplements all of that, usually worse.
2. **Why Zustand instead of Redux Toolkit or Context?** Almost all state here is server state (Query's job); the only pure client state is auth, which doesn't need Redux's ceremony. Context would work too, but Zustand avoids the re-render-everything-on-every-change problem Context has without `useMemo` discipline.
3. **Walk through the token-refresh interceptor.** `lib/api.ts` — a response interceptor catches a 401, and multiple concurrent 401s share one in-flight refresh promise (`refreshPromise ??= refreshAccessToken()`) instead of each firing their own refresh call; once it resolves, the original request retries with the new token.
4. **How does a page reload avoid bouncing a logged-in user to `/login`?** `useAuthBootstrap()` silently exchanges the refresh cookie for a new access token on app mount, before `ProtectedRoute` decides whether to redirect — it renders nothing until `isBootstrapped` is true.
5. **Why React Hook Form over controlled `useState` per field?** Uncontrolled-by-default inputs avoid a re-render per keystroke; `zodResolver` wires the same validation schema used conceptually on the backend directly into form state.
6. **Explain a real bug caused by uncontrolled form defaults.** The native `type="email"` HTML5 validation intercepted form submission before React Hook Form's `handleSubmit` ever ran — fixed with `noValidate` on the `<form>` (see Technical #8).
7. **How is routing structured, and why nested layouts?** `PublicLayout` (landing/auth) and `AppLayout` (sidebar + notification bell) each wrap their own `<Outlet/>`; `ProtectedRoute`/`PlatformAdminRoute` are their own nested layer so auth/role gating doesn't have to be repeated per page.
8. **How do you avoid prop-drilling the current user through every component?** `useAuthStore` is read directly wherever it's needed (e.g., `AppLayout`, `ProfilePage`) — Zustand doesn't need a Provider wrapper the way Context does, so there's no drilling problem to solve in the first place.
9. **How does the design system stay consistent across light/dark without a toggle?** CSS custom properties defined once in `:root` and redefined under `@media (prefers-color-scheme: dark)`, registered into Tailwind via `@theme inline` — components use semantic classes like `bg-surface`/`text-foreground`, never a literal color, so they never need per-component dark-mode variants.
10. **What's still not covered by tests on the frontend?** No component/unit tests yet — verification so far is TypeScript, `oxlint`, and manual Playwright checks against mocked API responses (documented in the Phase 6/7 commits), not an automated frontend test suite.

## Node.js / Express (10)

1. **How is async error handling centralized?** `asyncHandler()` wraps every controller and forwards rejected promises to `next(err)`; one `errorHandler` middleware at the bottom of the stack handles all of them, so no controller needs its own try/catch.
2. **Walk through the middleware order in `app.ts` and why it matters.** `helmet` → `cors` → `express.json` → `cookieParser` → `mongoSanitize` → rate limiter → routes → `notFoundHandler` → `errorHandler`. Body parsing has to happen before sanitization can inspect the body; error handling has to be last so it can catch everything upstream.
3. **How do you keep secrets out of the codebase?** `dotenv` + a Zod-validated `env.ts` that throws on startup if a required secret is missing or too short — fails fast at boot, not at first use in production.
4. **Why validate environment variables with Zod instead of just reading `process.env` directly?** A missing or malformed secret (e.g., a JWT secret under 32 characters) crashes the app immediately on startup with a clear message, instead of failing mysteriously the first time a token is signed.
5. **How is rate limiting layered across the API?** A blanket limiter on all of `/api`, plus tighter, route-specific limiters on `/auth` and the payment routes — each layer catches a different abuse pattern (general scraping vs. targeted credential/payment abuse).
6. **What does `express-mongo-sanitize` actually protect against, concretely?** A payload like `{email: {$gt: ""}}` sent as a login body — without sanitization, that object could be passed into a Mongoose query and match unintended documents; sanitize strips the `$gt` key before it reaches any query.
7. **Why constant-time comparison for the Razorpay signature, and what does `!==` actually leak?** A plain string `!==` typically short-circuits at the first mismatched character, so response time correlates with how many leading bytes were correct — an attacker can use that timing signal to reconstruct the correct value byte-by-byte. `crypto.timingSafeEqual` takes the same time regardless of where the mismatch is.
8. **How does the app avoid a Mongoose `CastError` becoming a raw 500?** `errorHandler.ts` checks `err instanceof mongoose.Error.CastError` and converts it to a proper `ApiError.badRequest()` before falling through to the generic 500 path.
9. **What's the request body size limit, and why bother?** `express.json({limit: '10kb'})` — a basic guard against a client (malicious or buggy) sending an oversized payload as a crude DoS vector.
10. **How would you add structured logging for production?** `morgan` currently logs HTTP access in `combined` format outside development; the next step would be a structured logger (pino/winston) with request IDs for tracing a request across services, which this app doesn't need yet at its current scale.

## About this project specifically (10)

1. **Why this project and not something more common?** Most student portfolios have a CRUD app or an e-commerce clone; almost none have a real ledger with concurrency-safe financial state transitions. It's a deliberately higher-rigor choice.
2. **What was the hardest part to get right?** The cycle-rollover logic in `contribution.service.ts` — one function has to correctly handle partial collection, full collection triggering a payout, opening the next cycle, and completing the circle on the last cycle, all as one coherent state transition.
3. **What's the one part of this codebase you understand best and could extend live in an interview?** The contribution/cycle rollover logic and its test suite — walk through `contribution.service.test.ts` scenario by scenario if asked to demonstrate it.
4. **Tell me about a time you found a real bug through testing, not just wrote tests for coverage.** Two, both genuine: the native-HTML5-validation form bug (Technical #8) and a timing-unsafe signature comparison found during a self-directed security pass (see Security #7 above) — neither was hunted for, both surfaced from actually running/reviewing the code.
5. **How did you handle a situation where you couldn't fully test something?** Directly — stated the limitation (no reachable database in the build sandbox), explained specifically why (checked two ways, documented in commit messages), and built the strongest alternative verification available (32 unit tests against mocked models) instead of either skipping verification or falsely claiming it was done.
6. **What would you tell a user this app *doesn't* do yet?** Send email reminders before a due date, or support bidding-based payout as an alternative to round-robin — both explicitly scoped out, not forgotten.
7. **How do you know the trust-score algorithm is "right"?** It isn't provably optimal — it's a simple, explainable, defensible first version (asymmetric penalty/reward, clamped range) chosen deliberately over something more complex for a v1. That's a legitimate answer if asked to justify it further.
8. **What's a tradeoff you made for the MVP that you'd revisit for v2?** Admin-confirmed contributions as the default — it's low-friction to build and demo, but it means the circle admin is a manual trust bottleneck; Razorpay integration exists specifically to reduce reliance on it.
9. **How would you demo this in an interview if you can't show a live deployment?** Walk through the unit test suite live (`npm run test`), and narrate the cycle-rollover test scenarios — it's a legitimate, concrete way to demonstrate the core logic works without needing a hosted database.
10. **What did building this teach you that a tutorial project wouldn't have?** Concrete example to have ready: reasoning about a specific concurrency scenario (double-contribution), then implementing and testing the actual database-level guard for it — not something a CRUD tutorial forces you to confront.
